R2 阵列桶实时统计设计

日期：2026-07-27 · 范围：R2 桶概览的数据口径与刷新行为

目标：WebDAV、S3 或程序内部上传完成后，已纳入阵列的桶在用户刷新或重新进入“桶概览”时，立即显示正确的对象数和存储用量。

问题与根因

“对象”页读取本地 r2_objects 已提交索引，因此上传完成后能立即看到对象；“桶概览”目前读取 Cloudflare GraphQL Analytics 的 r2StorageAdaptiveGroups，该数据存在不可控的统计延迟。同时，r2_physical_buckets.storage_bytes 只在接管或维护扫描结束时更新，不能作为上传后的实时统计。

选定方案

查询桶概览时，按物理桶实时聚合本地已提交对象，并用该结果覆盖已纳入阵列桶的行级统计。未纳入阵列的桶以及账号顶部总用量、免费额度仍使用 Cloudflare Analytics。

显示内容数据来源刷新语义
阵列桶用量、对象数本地 r2_objects 中 state = committed 的聚合立即一致
未纳入阵列的桶Cloudflare Analytics允许供应商统计延迟
账号总用量、免费额度Cloudflare Analytics允许供应商统计延迟

后端设计

  1. 在 R2 Store 增加按 physical_bucket_id 聚合的只读统计方法，返回 SUM(size) 和 COUNT(*)，仅包含 committed 对象。
  2. remoteBucketViews 同时读取物理桶、Cloudflare 桶列表、Cloudflare 用量和本地桶统计。
  3. 对于已纳入阵列的桶，payload_bytes 与 object_count 使用本地统计；空桶明确返回 0。Cloudflare 的元数据统计保持原值，因为本地索引没有等价口径。
  4. 对于未纳入阵列的桶，保留现有 Cloudflare 统计。远端已删除但本地仍登记的桶也显示本地统计，并继续标记异常。
  5. Cloudflare 用量查询失败时，阵列桶仍显示本地统计，账号总用量显示现有错误提示；本地统计查询失败时接口返回错误，避免伪造或沿用旧值。

前端设计

不增加轮询。右上角刷新继续重新加载当前页签；每次从其他页签重新进入“桶概览”时重新请求 /api/v1/r2/overview。一直停留在概览页时不会自动请求。

一致性边界

  • 上传只有在远端写入成功且本地对象状态提交后才计入统计。
  • 覆盖同名对象按最新已提交记录计为 1 个对象，并使用最新大小。
  • 删除开始后对象进入 deleting 状态，不再计入只包含 committed 的统计；失败与恢复继续沿用现有对象状态机。
  • 普通上传、服务端分片上传、WebDAV、S3 和复制操作共享同一索引，因此无需按协议维护独立计数器。
  • 接管扫描纳入的对象在写入本地索引后自然进入统计；再均衡只改变物理桶映射，下一次查询会反映到目标桶。

验证

  • Store 测试：只统计 committed；空桶为 0；多桶隔离；覆盖、删除和移动映射后的结果正确。
  • API 测试：阵列桶优先本地统计；未纳入桶保留远端统计；Cloudflare 用量失败时阵列统计仍可用。
  • 前端验证：首次进入、离开后重新进入、点击刷新都会重新请求；不产生定时轮询。
  • 回归验证：全量 Go 测试、前端构建及现有 WebDAV/S3 测试通过。

非目标

本次不改变 Cloudflare 账单统计口径，不增加后台同步任务，不引入缓存或持久化计数器，也不修改上传协议行为。
